The 1.4.0 stable release — everything since 1.3.9, rolling up the 1.4.0 beta line.

### Added

- Automatic retry of authenticated startup for launches that could not complete it — offline, locked device, or a transient auth failure. The SDK now retries on app resume, foreground, device unlock, network restoration, and successful token refresh, instead of staying idle until the next cold launch.
- A sensor health check at startup and on app foreground that detects and repairs HealthKit observers and background deliveries silently dropped by iOS.
- Dashboard visibility for previously swallowed sensor-pipeline failures (sensor store reads, observer arming, sensor probes, diagnostic reporting), with in-process de-duplication.

### Changed

- `enableSensors` is explicitly declarative: the passed set replaces the enabled set, including narrowing it — and the set is persisted before observers are armed, so a partial failure can no longer strand stored state. See the README for details.
- `deauthenticate` is idempotent and total: it succeeds whether or not the SDK is authenticated (or even configured), serializes concurrent calls, stops observers and background deliveries, and deterministically clears all profile-scoped state — the enabled sensor set, HealthKit anchors, queued uploads, cached demographic, and tokens — keeping only the device identifier. After re-authenticating, call `enableSensors` again.
- Auth-gated calls (such as `enableSensors` or `getScores`) made immediately after `configure` now wait for configuration to resolve instead of failing with a spurious "Unauthorized".
- `getSensorStatus` reports a sensor-store read failure through its error callback instead of silently returning `.pending`.
- `getStats` and `getSamples` are deprecated in favor of `getBiomarkers` — server-processed biomarkers are the supported read API.
- Stat and biomarker category taxonomies are aligned with the docs and the upload data-log types; the `activity_mid_intensity_duration` biomarker is renamed `activity_medium_intensity_duration`.

### Fixed

- **1.3.7 → 1.3.9 upgrades could silently stop collecting after one backfill**: 1.3.9 renamed 43 sensor raw values (nutrition and reproductive health) without migrating the persisted enabled-sensor set, so the set failed to decode on every read — and every read site swallowed the failure. The store now reads legacy names through a rename map, heals the persisted set in place, and reports the anomaly. HealthKit anchors saved under pre-rename keys are found again through read-time aliases, so collection resumes incrementally instead of re-backfilling.
- A timeout race in anchored HealthKit queries could permanently wedge sensor collection and cause iOS to suspend background delivery; anchored queries now cancel cooperatively in both collection coordinators.
- Sensor sets with no HealthKit-backed types (such as `[.device_lock]`) no longer fail `enableSensors` and `getSensorStatus` with "Health data types not specified".
- An upload cancelled mid-flight by deauthentication no longer re-persists its batch or posts a bogus "Max retry attempts exceeded" error.
- Stores disposed during logout can no longer write profile state back afterwards — tokens, the sensor set, anchors, and caches are all guarded.
- Error logs from wrapper SDKs report the wrapper framework as their location instead of `null`, and errors carry their original throw site rather than the SDK's internal logging helper.
- The `enableSensors` callback can no longer hang indefinitely when the permission flow stalls — it always reports back.
- Profile token refresh and session-expiry handling are hardened: a session is treated as expired only on corroborated evidence, never on a bare HTTP 400 response.
